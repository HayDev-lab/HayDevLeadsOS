# 4. IMPORTANT DISTINCTION

Activity Timeline и Domain Events — разные вещи.

## ACTIVITY

История действий вокруг lead:

```text
CALL
MESSAGE
NOTE
STAGE_CHANGE
```

## DOMAIN EVENT

Машиночитаемый бизнес-факт:

```text
FIRST_RESPONSE_BREACHED
FOLLOW_UP_OVERDUE
STAGE_BECAME_STALE
```

Не превращать Activity table в универсальный event bus.

Activity может быть presentation/audit history.

DomainEvent — системный контракт.

Payload должен содержать только данные, необходимые для:

* notification;
* audit;
* future automation.

```json

  "stageId": "...",
  "stageName": "Proposal",
  "overdueMinutes": 2880,
  "ownerId": "..."

```

Не копировать весь Lead object в JSON.

# 10. IMMUTABILITY

После создания DomainEvent не изменять его смысл.

Допустимо обновлять только технические processing fields.

Не делать:

```text
STALE event
→ превратить payload в recovered
```

# 11. IDEMPOTENCY

Критическое требование:

один переход состояния должен создавать только один DomainEvent.

Например:

Lead остаётся STALE 5 дней.

Нельзя каждые 5 минут создавать:

```text
STAGE_BECAME_STALE
STAGE_BECAME_STALE
STAGE_BECAME_STALE
```

---

# 12. DEDUPLICATION KEY

Использовать deterministic key.

Например:

```text
STAGE_BECAME_STALE:<leadId>:<stageEnteredAt>
```

Follow-up:

```text
FOLLOW_UP_OVERDUE:<taskId>:<dueAt>
```

First response:

```text
FIRST_RESPONSE_BREACHED:<leadId>:<lead.createdAt>
```

Assignment:

```text
LEAD_ASSIGNED:<leadId>:<assigneeId>:<assignmentVersion>
```

Адаптировать к реальной архитектуре.

# 21. EVENT RECONCILER

Создать service:

```text
runEventReconciliation()
```

Он:

1. загружает активные relevant entities;
2. использует существующие SLA engines;
3. определяет текущие состояния;
4. сравнивает с conditions для events;
5. создаёт отсутствующие DomainEvents idempotently;
6. создаёт Notifications через projector.

# 26. DO NOT REQUIRE PREVIOUS SNAPSHOT

Поскольку statuses динамические, event creation можно определять через deterministic deduplication.

Например:

если lead сейчас STALE:

попробовать создать event:

```text
STAGE_BECAME_STALE:<leadId>:<stageEnteredAt>
```

Если уже есть → no-op.

Это проще и надёжнее, чем хранить status snapshot только ради event detection.
